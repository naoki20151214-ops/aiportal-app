## AI Portal article production: mandatory no-duplicate gate
- Before writing ANY article, read `content/registry/knowledge-nodes.yml`, `content/registry/core-curriculum.yml` and `content/registry/article-production-workflow.md`.
- Obtain live GitHub inventory: `GITHUB_TOKEN=... npm run article:preflight -- BAS-0023` (substitute the real ID). Never interpret main `planned` as proof that no prior draft exists.
- If the command blocks for an article found in main, a retained draft/feat/preview branch or PR, STOP new drafting and reuse existing article, images and tests.
- For a PR importing a prior artifact, add `.github/article-reuse/<ID>.yml` with the exact original `sourceRef`. Never merge a preview-only PR.
- If GitHub cannot be scanned (no token, HTTP error, truncated tree), STOP; do not create an article on guesswork.
- `ready` is a technical preparation state, **not** user acceptance. Once the site owner says `合格`, treat that as production publication authorization, not immediate release: stage unchanged approved article/assets, record `decision: approved-for-publication` plus `publishOn: YYYY-MM-DD` (Japan-local publication date, earliest the next eligible day) in the approval ledger, and let the daily `publish-approved.yml` automatically validate and publish at most one article per calendar day. **Never ask for a separate publication approval.**
- Confirm the article is `ready` and queued with a valid future `publishOn` after approval; only once the date arrives confirm it became `published` on main and Cloudflare Production deployment succeeded. If prerequisites or safety checks block publication, report the blocked article and reason without re-requesting permission.
- The publication approval entry must contain `approvedBy: site-owner` and the exact immutable `sourceArticleBlob` of the staged `ready` article (obtain via `git hash-object content/articles/<slug>.md`). An altered article after sign-off must not publish. Retain the original review SHA separately when review→ready changes frontmatter.
- **2026-10-13 standing delegation:** For routine, low-risk evergreen educational articles, the site owner does NOT need to review every manuscript. A separate, evidence-backed editorial verification pass may approve publication by recording `approvedBy: editorial-qa`, `delegation: site-owner-standing-policy-2026-10-13`, exact ready `sourceArticleBlob`, `editorialAuditPath: content/editorial-audits/<ID>.yml`, and the audit Git `editorialAuditBlob`. The report must document independent source checks, all eight quality criteria, at least two verifiable source URLs cited in the manuscript, and zero unresolved blockers. Do not misrepresent an author's own review as independent. See `content/registry/delegated-editorial-policy.md` and `content/registry/editorial-audit-template.yml`.
- The immutable audited manuscript, distinct verification pass, GitHub CI and production prerequisites are mandatory. `ready`, plausible AI text, a syntactically complete template, or reader feedback is NEVER itself evidence of editorial sign-off. Fail closed on high-risk/news content, missing sources, safety concerns, and invalid audit provenance. Publish only through a latest-main release PR and the validated approval ledger.

## 2026-10-14 daily publication cadence (supersedes immediate-publish wording above)
- Prepare, QA, and merge approved ready articles ahead of time, but **do not publish when an approval PR is merged**. Every new pending approval must have `publishOn: YYYY-MM-DD` (Asia/Tokyo), no earlier than its planned slot.
- Production publisher is triggered by GitHub schedule at 20:00 JST (with manual recovery only), not by push. It will publish no more than **one** approved, dependency-safe and source-SHA-verified article per Japan calendar date, and won't publish before `publishOn`. Backlogs roll to future days rather than bursting.
- Only `published` frontmatter/Registry is exported publicly. The reviewed `ready` backlog stays non-public. No unofficial status changes and no bypass of audit, duplicate gate, source provenance, image or link checks.
- Explicit user approvals and standing-editorial delegations still authorize publication, but not same-day bypass. Continue publishing already-approved articles only through the daily workflow. Changes to release time are allowed as an explicit future policy update.
